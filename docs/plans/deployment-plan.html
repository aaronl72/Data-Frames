02

The only path between them

Local and cloud touch in exactly one place, and only in one direction.

The one design change this forces

In the all-Azure design, Wazuh sat inside an Azure VNet and reached the storage account over a service endpoint. On the ThinkPad it has to reach Azure across the internet — which punches a hole in the host-only isolation. So Wazuh needs two virtual NICs: one host-only facing the lab, one external restricted to Azure Storage. Every other VM stays host-only with no route out.

05

The cost that isn't money

Detection survives a closed laptop. Automation does not.

The honeypot keeps collecting into the airlock whether the ThinkPad is running or not, and Wazuh backfills on boot — so no data is ever lost. Detection is delayed, not missed.

But Shuffle isn't running at the moment the attack happens. You cannot demonstrate "Wazuh alerted at 03:14 and Shuffle blocked the source by 03:14:06" for any attack that occurred while the machine was closed — and a laptop is closed most of the time. Automated response is the differentiator in the pitch, and it is the specific thing this configuration cannot show retrospectively.

Closing the gap means moving Wazuh and Shuffle into Azure, which costs roughly $100/month more — not the smaller figure it might appear. They also cannot be split: Shuffle is triggered by Wazuh, so a local Wazuh that is switched off leaves an Azure Shuffle idle regardless. They move together or not at all.

Accepted for now: they stay local. The gap is real but it is a demo gap, not a data gap, and it only matters once there are prospect meetings to run. Learning the stack hands-on comes first.

06

What this changes in the accepted design

The four decisions accepted on 20 August assumed everything ran in Azure. Three survive the move; one changes shape.

DecisionUnder this planConsequence
D-01AmendedThe airlock now crosses the public internet instead of a service endpoint. Direction of initiation is preserved, so the control holds — but Wazuh needs a second NIC, and the storage account needs a firewall rule for your egress address rather than a service endpoint.
D-02aUnchangedHoneypot egress stays default-deny in Azure. R-13 unaffected.
D-02bStrengthenedA host-only virtual switch has no route to the internet at all, which is a harder guarantee than an NSG rule that could be mis-ordered. R-03 improves.
D-03Partly mootBastion still fronts the honeypot. The lab VMs no longer need it — you open the Hyper-V console.
D-04DowngradedWazuh and Shuffle move from Azure Backup to Hyper-V checkpoints plus a scheduled export. The BCP asks for "daily automated snapshots," which a scheduled task satisfies — but you now maintain it.

infra/bicep/modules/lab-network.bicep goes unused under this plan. It isn't wasted — it's the migration path if the lab later moves to Azure — but only the honeypot module deploys now.

07

Decide before creating the account

Each of these changes what gets provisioned. None of them are reversible for free once resources exist.

Do Wazuh and Shuffle run local or in Azure? Decided

Local for now; Azure is the target state. Learning Wazuh, Shuffle and T-Pot hands-on comes before paying ~$100/month for a machine to be awake at 3am. The automated-response gap is a demo constraint, and there are no prospect meetings to run yet. Revisit when there are — the honeypot data will already be a month deep by then.

Which identity creates the subscription?

Your stated position is a separate tenant per domain, on blast-radius-per-credential grounds. Worth knowing: data-frames.com is already a verified domain in an existing Microsoft 365 tenant — the MS=ms37433444 DNS record proves it. network-packets.com is not.

Free trial or pay-as-you-go?

The trial credit covers roughly the first four months of this plan, but converts to PAYG at expiry. Worth knowing which VM sizes are trial-eligible in Canada Central before building on them.

When does the 30-day clock start?

The honeypot needs about a month of continuous collection before the dashboards look like an operation rather than something switched on yesterday. That month is also what tuning takes. Standing it up early costs ~$45 and buys the demo.

08

Order of operations

Learning first, spending second. Steps 1 and 2 need no Azure account and can start today.

1

Wazuh on Hyper-V

All-in-one deployment, 8 GB. Put an agent on one target VM and get events flowing. This is where the real learning is — rule syntax, decoders, the noise problem, and why a fresh install generates thousands of alerts nobody should look at.

$0 · no Azure account needed
2

Shuffle, wired to Wazuh

Build the first playbook against your own lab alerts — enrich a source address, take an action, write a record. Attacking your own targets with Kali gives you a trigger on demand, so you can iterate without waiting for the internet to attack you.

$0 · still no Azure account
3

Honeypot to Azure — the clock starts

T-Pot needs a public address and real attackers, so this is the piece that cannot be learned locally. Deploy it early even though Wazuh isn't ready to consume it yet: the airlock accumulates immutably and Wazuh backfills later, so nothing is lost. A fresh public IP is typically scanned within minutes.

~$45/month · Azure account required here
4

Connect the airlock

Point local Wazuh at the storage account and pull. Now you are tuning rules against real attack traffic rather than synthetic tests — which is the month that turns a noisy install into something you would willingly show a prospect.

no change · ~$45/month
5

Lift Wazuh and Shuffle into Azure

Triggered by having meetings booked, not by a date. By then the rules are tuned, the playbooks work, and the honeypot data is already deep — so the move is a migration of something proven rather than an experiment you are paying to run.

~$150/month · when it earns it
